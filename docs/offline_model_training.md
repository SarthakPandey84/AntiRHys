# AntiRHys Offline Model Training & Evaluation Architecture

## 1. Executive Summary & Safety Policy
AntiRHys is an experimental, non-clinical driver vigilance and drowsiness monitoring prototype. In safety-critical contexts such as automotive operation, **continuous online learning or automated unreviewed retraining directly from production telemetry is strictly prohibited**.

### Core Safety Precepts:
1. **Zero Unreviewed Pseudo-Labeling:** Predictions generated by the heuristic detector (e.g., EAR drops, PERCLOS calculations) must never be treated as ground-truth labels for automated re-training. Doing so introduces catastrophic positive feedback loops, reinforcing false positives and overfitting to specific lighting or camera artifacts.
2. **Participant-Separated Partitions:** Datasets must strictly partition participants into separate Train, Validation, and Test cohorts. Random cross-validation at the frame level leads to profound data leakage (learning a driver's facial morphology rather than true physiological fatigue dynamics).
3. **Reproducible Offline Benchmarks:** All prospective model candidates (e.g., temporal LSTM, GRU, Temporal Convolutional Networks, or Transformer models) must be trained and evaluated in an isolated offline sandbox against fixed, versioned benchmark datasets with human-annotated ground truth.
4. **Strict Model Rollback Protocol:** A candidate model must outperform the production heuristic baseline across all key metrics (Precision, Recall, Detection Delay, False Alarm Rate) without any regression in edge-case tracking stability before being considered for canary deployment.

## 2. Training Dataset Schema & Feature Representation

The exported session logs (`session_log.csv` / `antirhys_all_sessions.json`) capture scalar ocular and head-pose telemetry without recording identifiable biometric imagery.

### 2.1 Tabular Schema Definition
Each recorded training row conforms to the following schema:

| Column Field | Type | Unit / Range | Description |
| :--- | :--- | :--- | :--- |
| `timestamp` | `ISO-8601` | UTC string | High-precision observation timestamp |
| `session_id` | `string` | UUID / hash | Unique session identifier |
| `event_type` | `string` | Enum | Observation type (`SAMPLE`, `STATE_CHANGE`, `DROWSINESS_ALERT`, etc.) |
| `severity` | `string` | Enum | `INFO`, `WARNING`, `CRITICAL`, `ERROR` |
| `detection_state` | `string` | Enum | `NORMAL`, `POSSIBLE_DROWSINESS`, `TRACKING_LOST` |
| `eye_state` | `string` | Enum | `OPEN`, `CLOSED`, `UNKNOWN` |
| `tracking_state` | `string` | Enum | `ACTIVE`, `LOST`, `SEARCHING` |
| `ear` | `float` | `[0.0, 0.6]` | Instantaneous Eye Aspect Ratio |
| `blink_count` | `int` | Count | Cumulative blinks in session |
| `closure_duration`| `float` | Seconds | Continuous sustained closure time |
| `perclos` | `float` | `[0.0, 1.0]` | Proportion of eye closure over 60s sliding window |
| `perclos_status` | `string` | Enum | `VALID`, `CALCULATING`, `INSUFFICIENT_DATA` |
| `ear_threshold` | `float` | `[0.18, 0.32]`| Active closure threshold |
| `calibration_state`| `string` | Enum | `IDLE`, `COLLECTING`, `COMPLETED`, `FAILED` |
| `detector_version` | `string` | Semver | Detector engine version |
| `notes` | `string` | Text | Diagnostic context or error descriptions |

### 2.2 Supervised Ground-Truth Annotation (`ground_truth_label`)
For offline supervised model training, data records must be augmented with verified human annotations:
- `0`: Alert / Attentive (eyes open, scanning road, responsive).
- `1`: Micro-sleep / Sustained Closure ($\ge 1.5\text{s}$ closure with verified physical relaxation).
- `2`: Head Drop / Postural Slump ($\ge 20^\circ$ downward pitch accompanied by low responsiveness).
- `-1`: Exclude / Corrupted (lens glare, heavy occlusion, extreme motion blur).

## 3. Participant Partitioning & Cross-Validation Strategy

Frame-level or temporal chunk random splitting is invalid for facial vigilance modeling. If frames from Driver A appear in both training and test sets, the model learns driver-specific facial geometry (e.g. hooded eyelids, epicanthic folds) rather than universal vigilance transitions.

### 3.1 Strict Cohort Splitting
- **Training Cohort (60% of participants):** Diverse group across biological sex, age brackets, eye shapes, and corrective lens usage (glasses/contact lenses).
- **Validation Cohort (20% of participants):** Independent participants used exclusively for hyperparameter tuning and early stopping.
- **Test Benchmark Cohort (20% of participants):** Held-out benchmark cohort evaluated only once per model candidate.

## 4. Evaluation Metrics & Benchmark Gates

Candidate models must be evaluated against the following multi-objective criteria:

### 4.1 Primary Quantitative Metrics
1. **Recall / Sensitivity ($\ge 95\%$ on sustained closures):** Proportion of true micro-sleeps or prolonged closures ($\ge 1.5\text{s}$) correctly detected.
2. **Precision ($\ge 90\%$):** Proportion of triggered alerts that correspond to true fatigue events.
3. **False Alarms per Hour (FA/hr $\le 1.0$ in alert driving):** Maximum allowable false alerts during normal alert driving under varied lighting (sunlight, tunnels, dusk).
4. **Alarm Latency / Detection Delay ($\le 1.8\text{s}$):** Elapsed time between true physiological eye closure onset and the audio-visual alert trigger.
5. **Inference Latency ($\le 25\text{ms}$ on CPU):** End-to-end execution budget per frame on lightweight edge/server CPU threads to maintain real-time 30 FPS capability.

---

## 5. Candidate Model Deployment & Rollback Protocol

Before promoting an offline trained model to production:
1. **Canary Shadow Mode:** Deploy candidate model in "shadow mode" where predictions are logged alongside the heuristic detector without triggering driver-facing alarms. Compare live agreement and false alarm rates for 100+ hours.
2. **Canary Deployment:** Enable driver alarms for a 5% user cohort.
3. **Automated Rollback Criteria:** Immediately revert to the validated heuristic baseline (`DrowsinessDetector` v2.1.0) if:
   - False alarm rate exceeds 2 per hour.
   - Inference latency spikes $> 50\text{ms}$ on $> 1\%$ of frames.
   - Any crash or unhandled exception occurs in inference thread.
   - User initiates baseline reset or reports spurious alert clusters.
